# 完整设计讨论

覆盖从"有一个想法"到"确定技术方案"的完整流程。三阶段按序进行，但允许跳过和回退。

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  ① 头脑风暴   │ ──→ │  ② 需求澄清   │ ──→ │  ③ 架构设计   │
│  (发散)       │     │  (收敛)       │     │  (决策)       │
│  brainstorming│     │  grill-me     │     │  architecture │
└──────────────┘     └──────────────┘     └──────────────┘
                           ↑                    │
                           └── 有缺口退回 ──────┘
```

---

## 三种模式

### 🌪️ 模式 1: Brainstorm（头脑风暴）

**目标**：产生尽可能多的想法，不评判
**触发**：用户说"brainstorm"、"发散一下"、"还有别的想法吗"，或需求模糊
**退出条件**：用户选中某个方向

**流程**：

```
1. 明确主题
   → "我们现在 brainstorm 什么？是关于 [X] 的不同实现方式，还是别的方向？"

2. 理解现状（参考 brainstorming skill）
   → 先看当前项目状态（文件、架构、最近 commit）
   → 问清楚一个问题再问下一个
   → 一次只问一个问题，优先用选择题

3. 疯狂输出
   → 抛出 5-8 个想法，不评判
   → 分类：技术方案 / 交互方式 / 数据流
   → 每个想法用 1-2 句话说清楚核心理念

4. 选出候选
   → "这几个想法里，哪个你最有兴趣深入？"
   → 用户选中 1-2 个 → 进入需求澄清
   → 用户说"够了" → 结束
```

**输出**：想法清单（通常不保存）

---

### 📋 模式 2: 需求澄清（联动 grill-me）

**目标**：把模糊想法变成可验证的需求，不留模糊地带
**触发**：Brainstorm 结束后自动进入，或用户说"拆解需求"
**退出条件**：所有分支都达成共识，无歧义需求

**流程**：

```
[STEP 1] 启动 grill-me
→ "现在进入需求澄清模式。我会像 grill-me 一样逐层追问，
   把 [选定想法] 的需求完全拆清楚。准备好了吗？"

[STEP 2] 逐层追问（参考 grill-me 风格）
   → 每次问一个问题，走完一个分支才进入下一个
   → 如果可以通过读代码验证，先读代码
   → 如果自己有推荐的答案，先说推荐
   
   ✅ 问什么：
   树形结构，按优先级依次探索：
   
   第一层（核心定位）
   - 用户是谁？在什么场景下使用？
   - 解决什么问题？不解决什么问题？
   - 和现有功能的关系是什么？（替换/增强/平行）
   
   第二层（边界约束）
   - 必须依赖的输入/数据？
   - 必须兼容的现有接口？
   - 性能/规模要求（如果有明确的数字标准）？
   
   第三层（验收标准）
   - 怎么算做完？
   - 如何验证它对用户有用？

[STEP 3] 输出需求文档
→ 需求确认无歧义后，汇总为结构化清单
→ 功能列表（Must / Should / Could）
→ 验收标准（每条可验证）
```

**输出**：需求文档（建议保存到 `docs/requirements/<feature>.md`）

**关键不变量**：
- 不写技术方案
- 不推测实现细节
- 如果一个分支 3 次追问都无明确答案，视为"暂不决定"，跳过

---

### 🏗️ 模式 3: 架构设计

**目标**：基于已确认的需求，确定技术方案并记录决策
**触发**：需求澄清完成后自动进入，或用户说"怎么实现"
**退出条件**：方案确认，或发现有需求缺口退回模式 2

**流程**：

```
[STEP 1] 理解现状（允许读代码，不写代码）
   → 读相关文件：入口、数据结构、现有类似实现
   → 读 CLAUDE.md 了解技术栈约束
   → 读 decisions.md 了解历史决策
   → 输出现状摘要（1-2 段）

[STEP 2] 约束分析
   → 技术栈：Tauri 2.x / Rust / Vanilla JS / 无框架
   → 兼容性：必须兼容现有数据格式？必须向后兼容？
   → 资源约束：开发时间估算
   → 列出明确的"不能做什么"

[STEP 3] 方案对比（≥2 个方案）
   → 每个方案各有 1 个明确的 tradeoff
   → 对比维度：复杂度 / 维护成本 / 扩展性 / 开发周期
   → 每个维度打分（1-3），用表格呈现：
   
   | 维度 | 方案 A | 方案 B | 方案 C |
   |------|--------|--------|--------|
   | 实现复杂度 | 低 | 中 | 高 |
   | 维护成本 | 低 | 高 | 中 |
   | 扩展性 | 中 | 高 | 高 |
   | 开发周期 | 1 天 | 3 天 | 5 天 |

[STEP 4] 推荐 + 决策
   → "我推荐方案 [X]，因为 [1-2 个最关键的 tradeoff]"
   → 询问用户是否同意
   → 如果用户有疑问，回到 STEP 3 补充对比

[STEP 5] 接口设计（如适用）
   → 前后端接口契约（Rust command / JS API）
   → 数据结构变更（JSON schema diff）
   → 数据流图（输入 → 处理 → 输出）

[STEP 6] 归档决策
   → 写入 decisions.md 活跃区
   → 格式见 decisions.md 规范
   → 标注影响范围（哪些文件/模块）
```

**输出**：架构方案 + 决策记录（追加到 `decisions.md`）

**关键不变量**：
- 不回头改需求——如果发现"这个需求做不了"，退回模式 2 补
- 读代码 ≠ 写代码——可以读来确定现状，但不实现
- 接口设计之前**必须有对比**——不允许只有一个方案

## 模式切换

### 自动切换

| 信号 | 当前 | → |
|------|------|---|
| "还有别的办法吗？" | 架构 | → Brainstorm |
| "换个思路" | 任何 | → Brainstorm |
| "选这个" / "这个有意思" | Brainstorm | → 需求澄清 |
| "怎么实现？" / "怎么做？" | 需求 | → 架构 |
| "这个需求其实不清楚" | 架构 | → 需求（退回）|
| "不需要讨论了" | 任何 | → 退出 |

**每次切换必须显性告知用户**："现在进入「XX」模式。"

### 手动触发

```
/brainstorm     → 模式 1
/requirement    → 模式 2（也可 trigger grill-me skill）
/architecture   → 模式 3
```

## 输出与协作

### 各模式输出

| 模式 | 输出物 | 保存 |
|------|--------|------|
| Brainstorm | 想法清单 | 临时，通常不保存 |
| 需求澄清 | 需求文档 | `docs/requirements/<feature>.md` |
| 架构 | 决策记录 | `.daily_reflection/decisions.md` |

### 与 BDD-TDD 的衔接

架构确认后主动询问：

> "架构已确定。是否进入 BDD-TDD 开发阶段？
> 1. 将验收标准转化为 Given-When-Then 场景
> 2. 将组件接口转化为测试清单
> 3. 开始实现"

### 与 daily-reflection 的衔接

- 需求文档保存后 → 提醒同步到 `daily-reflection` context-sync.json
- 决策记录写入后 → 检查 decisions.md 活跃区是否 > 8 条
