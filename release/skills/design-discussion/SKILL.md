# Design Discussion

覆盖从"有一个想法"到"确定技术方案"的完整设计流程。

## 三种子模式

### 🌪️ Brainstorm（头脑风暴）
- **目标**：产生尽可能多的想法
- **规则**：不评判、不限制、鼓励疯狂想法
- **输出**：想法清单
- **触发方式**：
  - 用户说 "brainstorm"、"brainstorm 一下"、"还有别的想法吗"
  - 讨论卡住，没有明显好方案
  - 用户说 "发散一下"、"再想想"
- **结束信号**：用户选中某个想法，或说"够了"、"开始评估"

### 📋 Requirement（需求拆解）
- **目标**：把模糊想法变成清晰、可验证的需求
- **规则**：追问为什么、划定边界、不写技术方案
- **输出**：功能列表 + 验收标准 + 优先级
- **触发方式**：
  - 默认入口（用户触发 skill 时，如果上下文不清晰）
  - 从 brainstorm 选中想法后
  - 用户说 "拆解需求"、"明确一下需求"
- **结束信号**：用户确认需求，或问"怎么实现"

### 🏗️ Architecture（架构讨论）
- **目标**：基于需求确定技术方案
- **规则**：评估 tradeoff、明确接口、不回头改需求（除非显式退回）
- **输出**：架构方案 + 接口契约 + 决策记录
- **触发方式**：
  - 需求确认后，用户问"怎么实现"
  - 用户直接说 "讨论架构"
  - 从 brainstorm 跳过需求直接讨论技术可行性
- **结束信号**：方案确认，或需要 brainstorm 找新思路

## 模式切换

### 自动检测

由 Claude 根据对话上下文判断是否需要切换模式：

| 用户信号 | 当前模式 | 切换方向 |
|---------|---------|---------|
| "还有别的办法吗？" | Architecture | → Brainstorm |
| "不知道选哪个" | Architecture | → Brainstorm |
| "这个可以试试" | Brainstorm | → Requirement / Architecture |
| "怎么实现？" | Requirement | → Architecture |
| "到底要什么？" | Architecture | → Requirement |
| "太局限了" | Architecture | → Brainstorm |

**切换时必须显性告知用户**："我们切换到 XX 模式。"

### 手动触发

用户可以随时说：
- `"brainstorm"` → 切到头脑风暴
- `"需求"` / `"requirement"` → 切到需求拆解
- `"架构"` / `"architecture"` → 切到架构讨论

## 各模式内部流程

### Brainstorm 流程

```
1. 明确主题 → 我们在 brainstorm 什么？
2. 疯狂输出 → 抛出 5-10 个想法，不评判
3. 分类整理 → 把想法归类（技术方案/交互方式/商业模式等）
4. 选出候选 → 让用户选出 1-3 个有兴趣的
```

### Requirement 流程

```
1. 理解场景 → 用户是谁？在什么情况下使用？
2. 功能列表 → Must / Should / Could
3. 验收标准 → 每个功能如何验证已完成？
4. 边界划定 → 明确不做什么
5. 优先级排序
```

### Architecture 流程

```
1. 理解现状 → 读代码、看已有架构（允许读取代码文件，不写代码）
2. 约束分析 → 性能、成本、时间、技术栈限制
3. 方案对比 → ≥2 个方案，维度：复杂度/维护成本/扩展性/开发周期
4. 接口设计 → 前后端契约、数据流
5. UI 原型（涉及界面变化时）→ 整理 Brainstorm 阶段产出的多个原型 HTML，或新写候选原型，放在 docs/prototypes/
6. 决策确认 → 记录最终选择及原因，**必须选定一个 UI 原型**（如果涉及界面变化），否则不能进入 BDD-TDD 阶段
```

> **UI 原型的定位**：所有探索过的原型都放在这里（按 `pbN-方案名-vN.html` 命名），包括最终选定的和废弃的。单人开发没有固定评审，开发过程中可能回退到其他方案，保留完整探索历史比只保留"最终选择"更有用。进入 BDD-TDD 开发后，Round 1 的"最薄实现"可能重写或复用选中的原型 HTML，由开发者自行决定。

#### Architecture 完成检查清单

设计文档写完后，逐条确认。全部 ☐ → ✅ 才能进入 BDD-TDD：

- [ ] **约束已明确** —— 什么不能动（技术栈、语义不可变字段等）
- [ ] **方案对比已完成** —— ≥2 个方案，各维度优劣列清楚
- [ ] **接口契约已定义** —— 输入、输出、数据格式有明确描述
- [ ] **数据流已明确** —— 用户操作到系统响应的完整链路
- [ ] **UI 原型已选定且保存到 `docs/prototypes/`** —— 涉及界面变化时，必须选定一个并归档
- [ ] **风险与缓解已记录** —— 至少列出 3 个已知风险及对应缓解措施
- [ ] **实施步骤（Stages）已拆解** —— 先做什么后做什么，依赖关系清晰
- [ ] **PB 验收标准已写入 `docs/pb/sprintN.md`** —— 后续 BDD 覆盖检查的对照基准

## 输出与文档

### 各模式输出

| 模式 | 输出物 | 保存建议 | 同步提醒 |
|------|--------|---------|---------|
| Brainstorm | 想法清单 + UI 草图/HTML 原型 | 临时，不强制保存；有价值的原型移入 `docs/prototypes/` | — |
| Requirement | 需求文档 | `docs/requirements/<feature>.md` | ⚠️ 保存后提醒同步 `daily-reflection` skill |
| Architecture | 架构方案 + 决策记录 + UI 原型 HTML（涉及界面变化时） | `docs/design.md` + `docs/prototypes/` | ⚠️ 保存后提醒同步 `daily-reflection` skill |

### 文档模板

模板的每个节同时也是讨论清单。写不下去 = 讨论时漏了相关内容——不要硬填，回头补讨论。

#### 需求文档

```markdown
# [需求] XXX

## 背景
...

## 用户场景
...

## 功能列表

### Must Have
- [ ] ...

### Should Have
- [ ] ...

### Could Have
- [ ] ...

## 验收标准
| 功能 | 验收条件 |
|------|---------|
| ...  | ...     |

## 边界（明确不做）
- ...
```

#### 架构决策记录

```markdown
# [架构决策] XXX

## 背景
现状是什么？为什么需要这个功能？

## 约束
技术栈、性能、时间、不可动的前提（如 status 语义只能由 quiz 决定）

## 方案对比
| 方案 | 优点 | 缺点 | 风险 |
|------|------|------|------|
| A    | ...  | ...  | ...  |
| B    | ...  | ...  | ...  |

涉及多个独立子问题时，每个子问题单独列表（如：存储位置 / 测试触发时机 / UI 形态）

## 最终选择
列出 MVP 范围 + 明确不做什么

## 接口契约
前后端命令、数据格式、关键流程的输入输出

## 数据流
用户操作到系统响应的完整链路，每个→都可以转为 BDD 场景

## 风险与缓解
单人开发没有评审，提前写下已知风险（如：LLM 输出非法 JSON、侧栏挤压主内容、Tab 切换状态错乱）

## 实施步骤（Stages）
按依赖关系拆解实施顺序，标注哪些可以并行
- Stage 1（基础设施）：纯后端 TDD，无 UI
- Stage 2（UI）：HTML 骨架 + 交互
- Stage 3（集成）：接入完整链路 + BDD/TDD

## 决策摘要
5-6 条关键决定，供 daily-reflection 引用
```

## 与 BDD-TDD Skill 的衔接

Architecture 模式结束后，主动询问是否进入开发阶段。衔接时明确产出物：

| 设计阶段产出 | BDD-TDD 中使用方式 |
|-------------|-------------------|
| 验证标准（Requirement） | → BDD 场景的 Given-When-Then |
| 接口契约（Architecture） | → TDD 测试的边界条件和异常路径 |
| 数据流（Architecture） | → BDD 场景的步骤串联 |
| UI 原型 HTML（涉及界面时） | → Round 1 的 HTML 骨架参考 |
| PB 验收标准（Sprint 规划） | → Round 3 全覆盖检查的对照基准 |

询问：

> "架构已确定。是否进入 BDD-TDD 开发阶段？我可以：
> 1. 将验收标准转化为 Given-When-Then 场景
> 2. 将组件接口转化为测试清单
> 3. 触发 BDD-TDD skill 开始开发"

## 注意事项

1. **模式必须显性** —— 每次切换模式时，明确告知用户"现在我们进入 XX 模式"
2. **不跨模式改需求** —— Architecture 模式下如果发现需求问题，显式说"这里有个需求缺口，我们退回 Requirement 模式补一下"
3. **允许跳过** —— 用户可以直接从 Brainstorm 跳到 Architecture，如果需求已经很清楚
4. **输出自动化** —— Requirement 和 Architecture 结束后，自动生成文档并询问保存位置
5. **读代码≠写代码** —— 讨论阶段允许读取代码文件来理解现状、验证假设，但不写实现代码
