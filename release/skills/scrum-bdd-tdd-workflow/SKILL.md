# Scrum + BDD + TDD 融合工作流

## 核心理念

三个层次在不同粒度上运作：

| 层次 | 解答的问题 | 工具 | 粒度 |
|------|-----------|------|------|
| **设计文档** | "系统长什么样？" | 架构文档、接口契约 | 模块边界、数据流 |
| **BDD** | "用户应该能做什么？" | Gherkin `.feature` 文件 | 端到端用户行为 |
| **TDD** | "代码行为是否正确？" | 单元测试 | 内部逻辑、边界情况 |

**Scrum 提供节奏，BDD 和 TDD 提供质量门禁。** 它们不是串行阶段——在每个 Sprint 中交织进行。

## 关键原则

1. **宏观设计先行，微观设计涌现。** 设计文档定义模块边界和接口方向。具体的字段格式、错误处理和边界情况在 BDD/TDD 中涌现。

2. **PB 是用户价值切片，不是模块。** 单个 PB 项（用户故事）通常跨越多个技术模块。PB 的 BDD 场景描述的是用户可见行为，不受模块边界限制。

3. **PB 级微循环（Walking Skeleton）。** 不要等所有 BDD 写完才开始编码，也不要按模块切分迭代。对每个 PB，从最薄的端到端路径开始（允许 stub/hardcode），每轮迭代都要能演示。逐步加厚：Walking Skeleton → 替换 stub → 异常处理。

4. **滚动规划。** 只详细拆分当前 Sprint。保留未来 PB 项为粗略标题。需求会漂移——过早的细节是浪费。

## 工作流：一个 Sprint 周期

### Sprint 规划

**输入：** 设计文档（模块边界、接口草图）
**输出：** 包含 PB 项 + 任务拆解的 Sprint Backlog

1. 阅读设计文档，识别涉及的模块。
2. 从**用户视角**（而非模块列表）编写 PB 项：
   ```
   "Agent 能在约束保护下执行实验"
   "实验结果自动评估并决定保留或回退"
   ```
3. **每条 PB 注明验收标准** — 从用户视角写 2-5 条可验证条件：
   ```
   PB: 科普意图识别与结构化内容生成
   验收标准:
   - 发送"科普一下金鱼"，收到 type:"science" 的 JSON 响应
   - 发送"什么是量子计算"，也触发科普模式
   - 普通消息（如"今天天气"）不受影响
   ```
   每条验收标准 = 后续 BDD 场景的源头。验收标准写清楚了，BDD 就有方向。
4. 对每个 PB 项，列出它涉及的模块。
5. 用故事点估算。一个 PB 项 = 多个模块的 BDD 场景。
6. **将 PB 拆解保存到 `docs/pb/sprintN.md`**（一个 sprint 一个文件），包含每个 PB 的验收标准，作为后续 BDD 覆盖检查的对照基准。

### Sprint 执行：PB 级微循环 (Walking Skeleton)

对每个 PB，按三轮迭代加厚：

```
PB 拆解为 3 轮迭代
        │
        ▼
Round 1: Walking Skeleton
  ├── 1-2 个 BDD 场景（仅正常路径）
  ├── TDD: 集成层测试（验证端到端链路通畅）
  ├── 实现: stub + 最薄实现
  └── ✅ 可演示
        │
        ▼
Round 2: 核心逻辑（可重复多轮）
  ├── 补充 BDD 场景（边界条件）
  ├── TDD: 模块级单元测试
  ├── 实现: 替换 stub → 真实实现
  └── ✅ 可演示 + 边界覆盖
        │
        ▼
Round 3: 异常处理
  ├── 补充 BDD 场景（异常路径）
  ├── TDD: 异常路径测试
  ├── 实现: 错误处理 / 降级
  └── ✅ 生产就绪
        │
        ▼
  BDD 全绿 + TDD 全绿 + 手动确认 → PB 完成
```

**关键规则：**
- 每轮结束时必须能演示端到端路径（哪怕 Round 1 用了 hardcode）
- Round 1 的 stub 代码可能被丢弃，但 BDD 场景和 TDD 测试保留——测试是契约，实现是细节
- 如果 Round 1 发现模块边界切错了，立刻回退修改设计文档。此时只写了 1-2 个场景，修改成本很低

**每日站会汇报 PB 进度，而非模块进度：**
```
"昨天：PB2 完成 Round 1——目录能点能跳，章节名 hardcode
 今天：PB2 Round 2——替换 ChapterParser，解析真实标题
 阻塞：跨模块的 anchor id 生成策略还没定，需要和团队对齐"
```
而不是：
```
"昨天：ChapterParser BDD 完成（3 个场景）
 今天：ScrollManager 的 TDD"
 // 听到这话没人知道 PB 做到哪了
```

#### 微循环中的反馈回路

实际开发中很少一路顺到底。BDD 场景写不下去、TDD 和 BDD 对不上、实现时发现遗漏——这些是常态。关键是遇到问题后往哪反馈：

```
              ┌──────────────────────────────┐
              │       设计文档                 │
              │  (模块边界、接口契约)           │
              └────┬───────────────▲──────────┘
                   │               │
                   ▼               │
              ┌────────────────────┴──┐
              │  BDD 场景              │
              │  (用户可见行为)         │
              └────┬───────────────▲───┘
                   │               │
                   ▼               │
              ┌────────────────────┴──┐
              │  TDD 测试              │
              │  (业务契约)            │
              └────┬───────────────▲───┘
                   │               │
                   ▼               │
              ┌────────────────────┴──┐
              │  实现 → 手动确认        │
              └────────────────────────┘
```

每一层向下推进时，发现的问题可以向上反馈。图中向上的箭头表示「需要用户确认」的决策点：

| 发现以下情况时 | 需要你确认的问题 |
|---------------|----------------|
| BDD 写不下去——模块边界不对 | 是用户需求理解错了，还是模块边界切错了？确认后决定改设计文档还是改 BDD |
| TDD 和 BDD 对不上 | BDD 描述的用户行为对不对？对→改设计文档和 TDD；不对→改 BDD 场景（你判断） |
| 实现发现 BDD 漏了边界情况 | 这个边界情况是否算一个独立的新增用户行为？是→补 BDD 场景再走 TDD。否→只补 TDD 测试 |
| 手动确认发现表现不对 | 是逻辑问题还是视觉问题？逻辑→补 TDD；视觉→直接改 |

### Sprint 评审

PB 验收通过需要满足以下条件，按顺序逐条确认：

1. **BDD 覆盖需求** — BDD feature 文件的场景覆盖了 PB 验收标准中的所有条件
2. **BDD 测试通过** — 所有场景已有对应的实现链路，验证通过
3. **TDD 覆盖率足够** — TDD 测试覆盖了 BDD 提炼出的所有业务契约（含正常路径 + 边界 + 异常）
4. **TDD 全绿通过** — 所有 TDD 测试通过
5. **用户手动确认** — 运行实际程序，手动操作验证 UI/交互符合预期

> **PB 通过 = BDD 覆盖 + BDD 通过 + TDD 覆盖 + TDD 全绿 + 手动确认**

### 完成定义（DoD）

```
[] 设计文档已更新（如果架构有变更）
[] BDD 场景覆盖 PB 验收标准
[] BDD 场景已编写并通过
[] TDD 测试覆盖 BDD 的所有业务契约
[] TDD 测试全部绿灯
[] 代码让所有测试通过
[] 手动验证通过（用户确认 UI/UX 符合预期）
```

## 三层如何映射

### 设计文档 -> BDD

设计文档说：`ConstraintEngine 验证参数范围。`

BDD 迫使具体化：
```gherkin
Scenario: 参数在范围内通过
  Given 配置要求 learning_rate 在 [0.0001, 0.1] 之间
  When 验证 learning_rate = 0.01
  Then 验证通过
```

编写此场景揭示了配置格式：`{"param_ranges": {"learning_rate": {"min": 0.0001, "max": 0.1}}}` — 一个设计文档中没有的设计细节。

### BDD -> TDD

一个 BDD 场景催生多个 TDD 测试：
- `test_param_within_range_passes`
- `test_param_below_min_blocked`
- `test_param_above_max_blocked`
- `test_multiple_params_one_violation`
- `test_unknown_param_ignored`

TDD 驱动内部 API 形态：`validate_params(params: dict) -> tuple[bool, str]`。

#### 边界说明：BDD 与 TDD 不是一一对应

| | BDD | TDD |
|---|---|---|
| **问什么** | 用户能做什么 | 业务契约是否遵守 |
| **粒度** | 端到端用户行为 | 规则、边界、异常 |
| **覆盖** | 一个场景描述一条验收路径 | 一个场景拆成多个测试（正常 + 边界 + 异常） |
| **示例** | "用户发送'科普一下金鱼'，收到结构化 JSON" | `test_keyword_what_is`, `test_missing_type_fails`, `test_json_with_code_block`... |

BDD 描述的是**用户可见的行为**。TDD 验证的是**支撑这些行为的业务契约**——规则、接口格式、容错策略。

一个 BDD 场景通常拆成 3-10 个 TDD 测试：
- 1 个正常路径测试
- 2-3 个边界条件测试（空值、极限值、特殊格式）
- 2-3 个异常路径测试（缺少字段、错误类型、解析失败）

#### pytest-bdd 可选

pytest-bdd 或 behave 能把 `.feature` 文件直接驱动的 step defs。但这只是实现手段，不是必要的：

| 方案 | 适用场景 |
|------|----------|
| pytest-bdd（step defs） | 团队协作，需要产品/QA 看懂 feature 文件 |
| 普通 `test_*.py` + `test_*.js` | 个人项目，或前端逻辑无 Python 后端可调用 |

**核心原则：** 是否用 step defs 不是关键，关键是 TDD 是否覆盖了 BDD 提炼出的所有业务逻辑（含正常路径 + 边界条件 + 异常处理）。

#### 测契约，不测实现

TDD 测试的是**业务契约**，不是**实现细节**。

| 值得测（契约） | 不值得测（实现） |
|---|---|
| 业务规则（关键词触发、格式校验、权限判断） | 仅为代码结构写的测试（比如"这里有个 if，给它补个测试"，而非从业务场景出发） |
| 边界情况（空值、极端值、异常格式） | 特定实现方式（用 setTimeout 还是 requestAnimationFrame） |
| 数据转换（JSON 解析、渲染计划、格式转换） | 纯赋值/调用/返回值传递 |
| 流程完整性（完成后调 onDone、异常时触发 fallback） | CSS 动画、视觉效果 |

#### 三层各自的职责边界

BDD、TDD、手动确认各自捕捉不同类型的错误。**三者的职责不重叠，不能互相替代：**

| 层 | 捕捉什么 | 用在哪里 | 检测方式 |
|----|---------|---------|---------|
| **BDD** | 用户行为路径对不对 | 端到端：输入 → 输出是否符合用户预期 | 自动运行场景 |
| **TDD** | 业务契约是否遵守 | 规则、边界、异常、数据格式、容错 | 自动运行测试 |
| **手动确认** | 看起来/感觉起来对不对 | 视觉表现、动画节奏、排版效果 | 人眼看 |

有些 Bug，BDD 和 TDD 全绿了依然存在。它们不是逻辑问题，而是表现问题。**这时候不是 BDD/TDD 覆盖不全，而是它们本来就不是干这个的。** 这也是为什么 Sprint 评审的最后一步必须是手动确认。

举例说明各层分别能发现什么：

| 场景 | Bug 的本质 | 会被哪一层发现 | 说明 |
|------|-----------|--------------|------|
| 打字机不动了 | 渲染/动画卡住 | 只有手动确认 | 数据逻辑正确，问题在视觉呈现 |
| 打完第三段后卡住 | 逻辑分支漏了 | TDD | 是后端/逻辑层的 Bug |
| 空消息导致白屏 | 前端容错缺失 | TDD（null check）或手动确认 | 既是逻辑问题也是表现问题 |
| 图片失败后布局错位 | CSS/渲染异常 | 只有手动确认 | 数据完整，视觉表现问题 |
| 打完后没触发 TTS | 事件触发链缺陷 | TDD | 流程完整性违约 |

**判断标准：这个 Bug 的本质是什么？**

- 如果它是**业务逻辑缺陷**（条件分支漏了、格式错了、容错没做）→ BDD/TDD 负责捕获
- 如果它是**表现/视觉缺陷**（动画不对、排版乱了、节奏不对）→ 手动确认负责捕获
- 如果两者兼有 → 逻辑部分用 TDD 锁定，表现部分靠手动

#### 自动化 vs 手动的取舍原则

知道了职责边界，接下来才是决策：如果一个 Bug 属于 BDD/TDD 的职责范围，到底要不要写自动化测试？

用三维判据决定：

| 维度 | 问什么 | 高 = 值得自动测 |
|------|--------|----------------|
| 触发复杂度 | 需要几步操作才能触发这个场景？ | ≥3 步或需要特定条件组合 |
| 回归风险 | 改相关代码时有多大概率再次引入？ | 高（关联模块多、改动频繁） |
| 手动成本 | 手工验证一次需要多长时间？ | ≥10 秒 |

**经验法则：**
- 手动验证 ≤3 秒 + 触发条件就是最简单的打开页面 → 不写自动化
- 触发需要 3 步以上，或手动验证需要 30 秒以上 → 写自动化
- 中间的灰度地带 → 看回归风险高低

UI/DOM 交互（按钮点击、面板弹窗、打字机逐字效果）属于**前端交互层**，手动验收效率更高，不需要写自动化测试。

### TDD -> 实现

失败的测试决定了要实现什么。没有失败的测试在前，就不写实现代码。

## 验证覆盖：BDD ↔ TDD ↔ PB

### 验证 TDD 覆盖了 BDD

TDD 是否覆盖了 BDD 提炼出的业务逻辑？用**追踪矩阵**来确认：

| BDD 场景 | 对应 TDD 测试 | 覆盖内容 |
|---|---|---|
| 科普请求返回结构化 JSON | `test_valid_response_passes`, `test_missing_type_fails`, `test_empty_content_fails`, `test_missing_title_fails`... | 正常路径 + 异常路径 |
| "什么是"触发科普 | `test_keyword_what_is` | 正常路径 |
| 非科普消息不受影响 | `test_non_science_message`, `test_normal_message_is_not_science` | 边界条件 |

**做法：**

1. **列 BDD 清单** — 每完成一个 BDD 场景就记录对应 TDD 测试
2. **查缺口** — 每个 BDD 场景至少对应：1 个正常路径 + 若干边界/异常测试
3. **TDD 命名规约** — 测试函数名体现对应的 BDD 场景（如 `test_keyword_what_is` 对应 "什么是" 场景）
4. **代码审查检查项** — 用 BDD 场景作为审查清单，逐个确认有 TDD 覆盖

> **判断标准：** 如果一个 BDD 场景描写的逻辑路径在 TDD 中没有对应的测试（至少正常路径），就是覆盖缺口。

### 验证 BDD 覆盖了 PB

PB 是**用户价值切片**，BDD 是**验收标准**。每个 PB 的验收标准必须对应到具体的 BDD 场景。

| PB 验收标准 | 对应 BDD 场景 |
|---|---|
| 发送"科普一下金鱼"收到 JSON 响应 | 用户请求科普金鱼，返回结构化 JSON |
| 发送"什么是量子计算"也触发科普 | 用户使用"什么是"触发科普 |
| 普通消息不受影响 | 非科普消息不受影响 |

**做法：**

1. **PB 验收标准 → BDD 场景** — 写 PB 时列出验收条件，每条对应至少一个 BDD 场景
2. **Sprint Review 演示脚本 = BDD 场景列表** — 不需要额外准备演示用例
3. **逐条确认**：BDD 覆盖 → BDD 通过 → TDD 覆盖 → TDD 全绿 → 手动确认

> **判断标准：** 如果 PB 的某条验收条件在 BDD 中没有对应的场景描述，就是覆盖缺口。

### 文件内的追踪标注

在 BDD feature 文件头部用注释标注对应的 PB：

```gherkin
# PB1: 科普意图识别与结构化内容生成
功能: 科普意图识别与结构化内容生成
```

在 TDD 测试文件中用类名或注释标注对应的 BDD 场景：

```python
# BDD: 用户请求科普金鱼，系统返回结构化 JSON
class TestValidResponseFormat:
    def test_valid_response_passes(self):
        ...
    def test_missing_type_fails(self):
        ...
```

---

### 一句话总结

> **PB → BDD**: 每个 PB 的验收条件写成一个或多个 BDD 场景
> **BDD → TDD**: 每个 BDD 场景拆成多个 TDD 测试（正常 + 边界 + 异常）
> **验证方法**: 追踪矩阵 + 命名规约 + 审查清单

## 要避免的反模式

| 反模式 | 为什么失败 | 正确做法 |
|--------|-----------|---------|
| 先写所有 BDD，再写所有 TDD，最后写所有代码 | 需求会漂移；过早的细节是错误的 | PB 级微循环（Walking Skeleton） |
| 按技术模块拆分 PB | 用户无法演示一个模块 | 按用户可见行为拆分 PB |
| 设计文档 = 完整规格说明 | 微观设计在编码过程中涌现 | 设计文档 = 骨架；细节在 BDD/TDD 中 |
| 跳过 BDD 直接写 TDD | 缺乏与利益相关者共享的验收语言 | BDD 先定义边界行为 |
| 只有 TDD 没有 BDD | 测试验证代码，而非用户价值 | BDD 定义构建什么；TDD 定义如何构建 |

```
│       └── sprintN.md          # Sprint N 的 PB 拆解（含验收标准）
├── tests/
│   ├── features/
│   │   └── pb1_*.feature       # 每个 PB 项的 Gherkin 场景
│   ├── step_defs/
│   │   └── test_pb1_*.py       # pytest-bdd step definitions
│   └── test_*.py               # 纯 TDD 单元测试

```

## 触发词

- "开始 Sprint" -> 设计文档映射到 PB，然后执行 PB 级 Walking Skeleton 微循环
- "写 BDD" -> 为当前 PB 项编写 Gherkin 场景
- "写 TDD" -> 为当前 PB 编写红-绿-重构测试
- "规划 backlog" -> 从设计文档提取用户价值的 PB 项
- "BDD 和 TDD 如何配合" -> 解释三层模型
- "是否需要先完成所有设计再编码" -> 解释涌现式微观设计
